Iron Forest

Software factory — architecture from first principles

Misty Step2026-08-04Design review draft 6 reference systems studied3 proposals

A software factory converts human intent into released software without a human watching every step. Its one hard constraint: the producer is nondeterministic and occasionally wrong, yet the effects must be exactly once and the spend bounded. Everything in this document derives from that tension.

Method

This design is derived from the problem, not from prior decisions. No existing roadmap, doctrine, or predecessor system is treated as binding. Where another system is named, it is evidence of what happens in practice — a corroboration or a caution — never an authority. Where an in-house service could play a role, it appears only as an integration option chosen on the merits.

01Recommendation

Build Proposal A (Chain): one Go binary, a SQLite-WAL ledger, a linear pipeline of phases. Design the scheduler and the transport as explicit seams so Proposal B (Graph) is a scheduler swap and Proposal C (Fleet) is a deployment change. Do not build any of them until the requirements in §03 are accepted, because each requirement has a price and an alternative.

Scope
One deep service: durable run execution, trace, and cost attribution. Nothing else.
Language
Go for the orchestrator. The agent stays a subprocess in its own language.
Ledger
SQLite in WAL mode. One file. Readers poll a monotonic cursor.
Harness
opencode by default, behind a nine-line Harness interface. Other agents swappable.
Model
deepseek/deepseek-v4-flash-0731 through OpenRouter, with a cascade fallback.
Secrets
Injected at the egress by a broker the factory trusts. The agent never holds a provider key.
Work intake
Claim work from the operator's existing work system. The factory stores no backlog.
Substrate
One server. The same binary runs on a desktop with no code change.
First proof
One one-phase run and one five-phase run on the same request, with cost, time, and acceptance compared.

Why this shape

  • A linear pipeline is the honest starting topology. Every working system in the landscape ships a linear phase list. Branching and parallelism are later, optional, and costly. There is no published evidence that a multi-lane pipeline beats a linear one for real work, so start where the evidence is and measure before diverging.
  • Go is the right orchestrator language, and the choice is unrelated to the agent. Every system in the landscape separates the orchestrator from the agent runtime. Go gives one static binary, real concurrency, and no runtime to install. It has no mature coding-agent library, and it does not need one; the agent runs as a subprocess.
  • SQLite removes an entire class of failure. A durable ledger with two constraints — effects happen exactly once, and the log is the truth — needs either a battle-tested store or a long list of invariants you defend yourself. SQLite is the first. An external workflow engine is the second, plus an operational dependency. This design does not need an event-sourcing engine to run a pipeline.
  • Cost attribution is not a feature; it is a precondition. You cannot decide whether a phase earns its place unless the run records what it spent. So spend is attached to every run from the first line of code.
Sharpest risk

The factory will add stages because stages are easy to define, and nobody has measured whether they help. A five-phase pipeline can be worse than one competent agent with a good prompt: more tokens, more chances to misread a handoff, more gates to trip.

So the workflow file must be able to declare a one-phase control arm of itself, and a run must be able to execute that arm on the same request. Then "does this pipeline deserve to exist" is a query against the ledger, not a debate.

02Two ground truths

Two facts are not assumptions; they are the fixed points every decision below orbits.

G1 · The producer is nondeterministic and occasionally wrong

An LLM returns a plausible next token, not a guarantee. It will misread an instruction, edit the wrong file, claim a test passed that did not, and invent an API that does not exist. Probing is cheap and honesty is cheap, but neither is guaranteed. No amount of prompt care removes this. The design must therefore assume the agent is both wrong sometimes and creative in ways its author did not predict.

Consequence: everything the factory relies on — sequencing, retries, acceptance, mutation — must be deterministic code that the agent cannot reach. The agent proposes; code disposes.

G2 · Effects must happen exactly once

A run touches real state: commits, PRs, reviews, maybe a merge. If the factory retries a phase after a crash and the phase had already performed its effect, the state is now wrong twice. Duplicate PRs, duplicate commits, and double-charged model calls are all the same failure: an effect that was not idempotent was repeated.

Consequence: each effect must be idempotent or gated by a record in the ledger, and a resume must start at the last committed phase boundary, never earlier.

Every requirement in §03 and every theorem in §05 is a direct consequence of G1 or G2.

03Requirements, derived

From G1 and G2, plus the stated wish to run unattended, see and manage costs, read full traces, talk to GitHub, and run on a server or a desktop, the requirements are:

These nine are the acceptance list. A proposal earns its code by how well it satisfies R1–R9 at the smallest cost in moving parts.

What the landscape teaches, stated as observations not law

warren

  • WORKS Four sides of an agent: mind (persona), memory (expertise), worklist (tasks), body (loop + tools). Clean decomposition that survives contact with real repos.
  • WORKS The resolved agent is frozen onto the run row. A mid-run config edit does not affect an in-flight run.
  • WORKS One event stream, three thin clients. UI, CLI, and HTTP read the same stream.
  • WORKS A distinct empty-push event. A push that landed nothing is observably different from real work.
  • STRUGGLES Two isolation backends (bwrap and K8s) double the surface; a feature stops working under one of them and goes unnoticed.
  • STRUGGLES A single bearer token with no rotation, expiry, or scopes.

fabro

  • WORKS The workflow is a diffable, reviewable, version-controlled file. Graphviz DOT renders it for free.
  • WORKS CSS-like model stylesheets: * { model: cheap } then .coding { model: frontier }. Route cost with one line.
  • WORKS Human approval is a node shape, not an out-of-band interrupt.
  • WORKS A git checkpoint per stage. Resume, revert, or trace any change.
  • STRUGGLES DOT has no schema and no types; validating a workflow requires your own parser.
  • STRUGGLES A hard dependency on one sandbox vendor.

super-simple-software-factory

  • WORKS "Agent proposes, code disposes." The best sentence in the corpus and the same shape as G1.
  • WORKS Phases default to fail. Success has to be earned by a clean exit, a parsed envelope, and green gates.
  • WORKS A correction re-prompts the live session; a cold restart discards everything the agent learned.
  • WORKS The whole transport is one cursor query: select new events after a row id. No websocket, no ingest endpoint, no replay path.
  • WORKS Gates verify claims after the fact, never predictions.
  • WORKS A read-only agent is enforced by diffing and rolling back the repo, not by asking nicely.
  • STRUGGLES No sandbox, no branch per run, no merge step. Its own README lists these as missing.
  • STRUGGLES Placeholder quality commands that exit 0. A green phase that ran nothing is worse than no phase.

buzz

  • WORKS Humans and agents are the same kind of actor with different keys. Scope by identity, not by permission flags.
  • WORKS The hash-chained audit log with a single-writer advisory lock.
  • WORKS Loop prevention. Workflow-emitted events must not trigger workflows.
  • STRUGGLES The whole substrate. Nostr, relays, Postgres, Redis, and S3 to run a coding agent is more moving parts than the problem needs.
  • STRUGGLES Ships approval gates whose engine marks the run failed instead of parking it. Its docs call this out.

olympus — strongest safety shape in the landscape

  • WORKS A wake cause is not authority. A webhook is a hint; the controller re-reads the source before admission and before every mutation. This removes a whole class of stale-intent bug.
  • WORKS An in-process egress LLM proxy: server-side key injection, per-run bearer tokens with a TTL, hashed at rest, scoped to a workflow and target, with a request cap and usage rows.
  • WORKS Per-agent permission maps. The reviewer gets bash: deny and edit on one path only.
  • WORKS Exact-SHA worktrees plus a host flock. Physical serialization beats a distributed lock at this scale.
  • WORKS Publish once, then poll for the exact published SHA. Never republish.
  • WORKS Append-only ledger enforced in SQL with RAISE(ABORT) triggers.
  • STRUGGLES Three hard-coded workflows with bespoke controllers; adding a workflow means controller surgery.
  • STRUGGLES Monitors added reactively after each incident instead of designed-in telemetry.

bitterblossom — the post-mortem

  • WORKS Schema as the trust boundary. Cross-field invariants mean an evidence packet cannot claim a merge it did not perform.
  • WORKS One terminal tool call as the only completion channel; exactly one call or the phase fails.
  • WORKS A head-SHA contract enforced inside the child, so an engine retry re-validates reality.
  • WORKS Idempotent findings via a content marker.
  • WORKS A positive environment allowlist to the agent subprocess. Orchestrator tokens never cross.
  • WORKS Model family varies across review lanes. Same-family lanes are correlated noise.
  • STRUGGLES A pinned immature workflow engine, then four separate workarounds for engine defects.
  • STRUGGLES Zero dollar attribution on unattended multi-hour runs.
What the landscape says together

Six independent systems, no shared lineage, and the ones that survived converged on the same moves: control in deterministic code, typed handoffs, post-hoc gates, correction over restart, and a durable event log. The ones that struggled did so in predictable places: immature infrastructure, unbounded spend, and bespoke controls. The next section turns that agreement into theorems with reasons.

05Seven theorems

Each theorem states a rule, the failure it prevents, and the reason the rule is necessary. The reason is the argument; the landscape is only a note that the failure has been seen.

T1 · Control is deterministic; the agent is a subprocess behind a seam
Sequencing, retries, budgets, and acceptance live in code. An agent phase starts, runs bounded, and returns a typed value.
Failure prevented: behavior encoded in prompt prose. That behavior cannot be tested, reviewed, or reasoned about, and it changes when the model changes.
T2 · The agent proposes; code disposes. Values cross seams as typed envelopes
A phase returns a value parsed against a schema. Free text never crosses a boundary; anything unparseable fails the phase.
Failure prevented: the phantom claim. An agent asserts "merged" or "tests pass" in prose, and downstream code trusts the prose. Every handoff then silently depends on the model's honesty.
T3 · No agent-authorized external mutation
The agent never holds the authority to change external state. It produces a typed value; deterministic publisher code performs the mutation, idempotently, gated by the ledger.
Failure prevented: a model that is wrong in a confident way makes an irreversible external change. This is the most expensive failure this system can have.
T4 · Gates verify after the fact
A gate runs after a phase finishes and checks the envelope's claims against reality: did the artifact appear, does the diff match the claim, do the seeds fail without the change.
Failure prevented: pre-flight checks and "trust me" exhaust. You cannot know what an agent touched until it actually touches it, so only after-the-fact inspection is honest. Post-hoc gates are also how G1's occasionally-wrong producer gets contained.
T5 · A correction beats a restart
When a gate fails, re-prompt the same agent session with the exact violation and the gate report, and resume the phase. A cap on rounds stops the loop.
Failure prevented: the cold-restart tax. Starting a new session throws away the context window — the one resource the agent already paid for — and it repeats the same mistake with new confidence.
T6 · The durable event log is the single source of truth
Every event is appended while the work happens. Live view and historical replay are the same query at two cadences: "give me events after cursor." No ingest endpoint, no duplicate path.
Failure prevented: live and history disagreeing, which always ends in a wrong operator decision about a real run.
T7 · An event is a hint; the source is the authority
A timer, webhook, or card is a request to check reality. Before admission and before each mutation, read the real source: is the branch still there, is the PR still open, is this still unclaimed?
Failure prevented: executing stale intent. The classic case is a webhook from an event the factory itself produced, or acting on a card another actor already claimed.
Design test

A proposal that violates one of these seven is wrong, in this order of severity: T3 first, then T4, then T7, then T1, then T2, then T5, then T6. If a shortcut name sounds tempting — "just let the agent push to main" — it is violating T3, and the penalty is an irreversible external effect.

06The object model

Six nouns. Everything else is derived.

  AGENT      a named role. purpose + system prompt + model cascade + tool policy + write boundary.
             never a model id at the call site.

  PHASE      one bounded step. kind = agent | code | gate | human.
             defaults to fail. success is earned.

  WORKFLOW   an ordered list of phases (A), or a DAG of them (B).
             a versioned file in the target repository.

  ENVELOPE   the typed value a phase returns. parsed against a schema.
             the only channel that crosses a seam.

  GATE       gate(envelope, run) -> report. verifies claims. runs after.

  RUN        one execution. owns a workspace, a branch, a budget, a ledger stream,
             and one claimed piece of work.

Agent definition

One YAML file per roster. Config says who an agent is. The workflow says how it is used.

defaults:
  harness: opencode
  model:   [deepseek/deepseek-v4-flash-0731]   # cascade; index 1+ are fallbacks
  variant: medium                              # reasoning effort
  protected:                                   # no agent may edit the machinery that grades it
    - .forest/
    - workflows/

agents:
  - name: planner
    purpose: Turn a request into a plan the builder implements without asking questions.
    model:   [deepseek/deepseek-v4-flash-0731, z-ai/glm-5.2]
    variant: high
    writes:  [specs/]            # enforced by post-call diff, then rollback
    tools:   {deny: [bash]}
    output:  PlanOutput

  - name: reviewer
    purpose: Judge whether the change is what was asked for.
    model:   [x-ai/grok-4.5]     # different family on purpose: same-family lanes correlate
    writes:  []                  # read-only, enforced in code
    tools:   {deny: [bash, edit, write]}
    output:  ReviewOutput

Workflow definition

Lives in the target repository, so it is reviewed like source.

name:     plan-build-verify
budget:   {usd: 2.00, on_exceed: cancel}
control:  direct              # the one-phase baseline this pipeline is measured against

phases:
  - {name: plan,    kind: agent, agent: planner}
  - {name: build,   kind: agent, agent: builder, mutates_head: true}
  - {name: gate,    kind: gate,  checks: [artifacts_exist, diff_matches_claims]}
  - {name: test,    kind: code,  run: quality.test}
  - {name: fix,     kind: agent, agent: builder, on_fail: test, max_rounds: 2, resume: true}
  - {name: review,  kind: agent, agent: reviewer}
  - {name: commit,  kind: code,  run: git.commit}
  - {name: publish, kind: code,  run: github.open_pr}

# the control arm. same request, same budget, one phase.
controls:
  direct:
    phases:
      - {name: do, kind: agent, agent: builder, mutates_head: true}
      - {name: commit,  kind: code, run: git.commit}
      - {name: publish, kind: code, run: github.open_pr}
Note the control block

This is the answer to "does my pipeline earn its phases?" expressed as data. Any workflow can run as its own control arm on the same request. Cost, wall time, and acceptance are already in the ledger, so the comparison is a query, not a project. If the five-phase arm is not measurably better, delete the phases.

Go interfaces

Three seams. Everything swappable sits behind one of them.

// Harness runs one bounded agent phase and streams events. The only seam between
// the deterministic orchestrator and an opaque coding agent.
type Harness interface {
    Name() string
    Run(ctx context.Context, req PhaseRequest, sink EventSink) (PhaseResult, error)
}

type PhaseRequest struct {
    Workspace  string        // absolute path; the agent's cwd
    System     string        // rendered system prompt
    Prompt     string        // rendered user prompt
    Model      string        // resolved from the cascade at dispatch, then frozen
    Variant    string        // reasoning effort
    SessionID  string        // "" = new. non-empty = resume, for corrections.
    Tools      ToolPolicy    // allow / deny / no-builtins
    Output     *jsonschema.Schema
    Deadline   time.Time
}

type PhaseResult struct {
    SessionID string          // carried forward so a correction reuses the window
    Envelope  json.RawMessage
    Usage     Usage           // in, out, cacheRead, cacheWrite
    CostUSD   float64
    ExitCode  int
}

// Gate verifies an envelope's claims against reality. Always after the call.
type Gate func(ctx context.Context, env Envelope, run *Run) GateReport

// Ledger is the single durable store. Append-only for events.
type Ledger interface {
    StartRun(context.Context, RunSpec) (*Run, error)
    Append(context.Context, Event) error
    Since(ctx context.Context, runID string, cursor int64, limit int) ([]Event, error)
    FinishPhase(context.Context, PhaseID, PhaseResult, []GateReport) error
}

Ledger schema

SQLite, WAL. Events are append-only and enforced in SQL.

CREATE TABLE runs (
  id          TEXT PRIMARY KEY,
  workflow    TEXT NOT NULL,
  arm         TEXT NOT NULL DEFAULT 'main',   -- 'main' | control-arm name
  work_id     TEXT,                            -- claimed work item, if any
  repo        TEXT NOT NULL,
  base_sha    TEXT NOT NULL,
  branch      TEXT NOT NULL,
  state       TEXT NOT NULL,                   -- queued|running|blocked|done|failed|cancelled
  accepted    INTEGER,                         -- distinct from state: phases pass and the run still fails
  budget_usd  REAL,
  cost_usd    REAL NOT NULL DEFAULT 0,
  tokens_in   INTEGER NOT NULL DEFAULT 0,
  tokens_out  INTEGER NOT NULL DEFAULT 0,
  created_at  INTEGER NOT NULL,
  ended_at    INTEGER
);

CREATE TABLE phases (
  id          TEXT PRIMARY KEY,
  run_id      TEXT NOT NULL REFERENCES runs(id),
  seq         INTEGER NOT NULL,
  round       INTEGER NOT NULL DEFAULT 0,
  name        TEXT NOT NULL,
  kind        TEXT NOT NULL,                   -- agent|code|gate|human
  agent       TEXT,                            -- roster name
  model       TEXT,                            -- resolved, frozen
  session_id  TEXT,                            -- harness session; enables correction
  status      TEXT NOT NULL DEFAULT 'fail',    -- success is earned
  sha_before  TEXT, sha_after TEXT,
  cost_usd    REAL, tokens_in INTEGER, tokens_out INTEGER,
  started_at  INTEGER, ended_at INTEGER
);

CREATE TABLE events (
  seq       INTEGER PRIMARY KEY AUTOINCREMENT,  -- the cursor. the whole transport.
  run_id    TEXT NOT NULL,
  phase_id  TEXT,
  parent    INTEGER,                            -- nests tool calls under a phase
  ts        INTEGER NOT NULL,
  kind      TEXT NOT NULL,
  name      TEXT,
  payload   TEXT NOT NULL
);
CREATE TRIGGER events_immutable BEFORE UPDATE ON events
  BEGIN SELECT RAISE(ABORT,'events are append-only'); END;

CREATE TABLE envelopes    (phase_id TEXT PRIMARY KEY, schema TEXT, body TEXT, valid INTEGER);
CREATE TABLE gate_results (id INTEGER PRIMARY KEY, phase_id TEXT, gate TEXT, ok INTEGER, checks TEXT);

The entire live-view transport is one statement:

SELECT * FROM events WHERE run_id = ? AND seq > ? ORDER BY seq LIMIT 500;

Live view and full history are the same query at two cadences. There is no ingest endpoint, no websocket, no backfill, and no separate replay path. Every reader opens WAL, so reads never block a running writer.

Run lifecycle

  intake      claimed work, cron tick, or GitHub webhook.
     │        the cause is a HINT (T7).
     ▼
  admit       re-read the real source. is it still real? still unclaimed? (T7)
     │        claim the work. check budget. take the per-repo lock.
     ▼
  provision   git worktree at an exact base SHA. branch forest/<run>.
     │        seed .forest/context/ with prior envelopes.
     ▼
  phases      for each phase:
     │          agent → Harness.Run(), parse envelope, run gates
     │                  on violation → re-prompt SAME session with the report (T5)
     │          code  → deterministic step, its own trace row
     │          gate  → verify the previous envelope's claims (T4)
     │          human → park the run, wait, resume on decision
     │        every event → ledger, while it happens (T6)
     ▼
  publish     deterministic only. commit, push, open PR, post findings (T2, T3).
     │        idempotent content marker. publish once, poll for the exact SHA.
     ▼
  settle      accepted? write terminal evidence. release the worktree.
              never release the claim implicitly; report it.

Scheduler
Walk the phase list. One run per repo at a time, enforced by a file lock. N runs across repos.
Durability
Every phase boundary commits to SQLite. On boot, resume from the last committed phase; mark orphans interrupted and never replay a mutation.
Concurrency
Worker goroutines. One SQLite writer through a single connection. Agents are subprocesses, so a hung agent cannot wedge the orchestrator.
Deploy
scp the binary. Systemd unit. One server. Identical on a desktop.

Strengths

  • Smallest correct thing. One binary, one file, one process.
  • Covers every requirement R1–R9: agents, workflows, cost, traces, GitHub, server, desktop.
  • Deterministic phases are a node kind, not a special case.
  • No external engine, so no engine defects to work around; the ledger is yours and simple.
  • The control-arm comparison is a query, because both arms write the same ledger.

Limits

  • No parallel fan-out inside one run. Three reviewers run in sequence.
  • No conditional branching beyond a bounded fix loop.
  • One host caps concurrency at what one box can sandbox.

Pick when the workflow is a pipeline, which describes every workflow this factory needs today.

Replace the list-walker with a topological scheduler. The ledger, harness, gates, and publisher do not change.

Strengths

  • Human approval becomes a first-class, resumable state.
  • Matches the strongest proven graph shape in the landscape without its untyped authoring or its sandbox vendor.

Limits

  • Concurrent phases in one worktree collide. Each parallel node needs its own worktree and a merge step.
  • Failure semantics harden: partial fan-out, sibling cancellation, and barrier timeouts.
  • A parked human gate can hold a lock and a budget reservation for days.

Pick when you have measured that multi-lane review beats single-lane review. Not before.

  │            │              │              --worker)
  └ sandbox    └ sandbox      └ sandbox
    + harness    + harness      + harness

  the worker holds NO secret. every model call goes back through
  the control plane's egress proxy on a per-run token with a TTL.
Adds
A worker protocol, lease and heartbeat, work stealing, and worker-side event push.
Store
Postgres once more than one process writes. Or keep SQLite with exactly one writer and stream reads.
Nice property
Your desktop joins as a worker with one flag. That is the clean answer to "maybe run on someone's desktop."

Strengths

  • Concurrency is no longer capped by one box.
  • A runaway agent kills its worker, not the control plane.
  • Heterogeneous workers: a cheap server for small phases, a big one for builds.

Limits

  • You now own a distributed system: leases, split brain, partial failure, and worker auth.
  • This is where the landscape's strongest system needed a cluster. That is the cost of this tier.
  • Unjustified until one box is provably saturated.

Pick when a measured queue depth on one server is the actual bottleneck. Not on a forecast.

Verdict

Default to opencode. It is the only candidate with all six properties an unattended orchestrator needs: JSON events, session resume, per-call model and effort, named agents, an unattended permission model, and first-party cost reporting. It also has MCP and a headless server.

Keep goose as the MCP-heavy alternate. Its recipe-plus-sub-recipe model with typed --params is the best agent-definition surface of the four, and it is a static Rust binary with no runtime.

Keep pi as a reference bounded node. Two public systems chose it. Its deliberate absence of MCP is a smaller tool surface to audit, which suits a read-only reviewer.

Treat omp as a possible in-house path only if you want the factory coupled to the OMP runtime. Its recipes already express models, skills, and MCP servers in one bundle.

The interface is nine lines. Write all four adapters; pick per agent, per phase.

agents:
  - {name: builder,  harness: opencode, model: [deepseek/deepseek-v4-flash-0731]}
  - {name: reviewer, harness: pi,       model: [x-ai/grok-4.5], tools: {deny: [bash, edit]}}
  - {name: triager,  harness: goose,    model: [deepseek/deepseek-v4-flash-0731]}   # needs GitHub MCP
Language reality check

Go has no mature coding-agent harness, and it does not need one. Every system in the landscape separates the orchestrator language from the agent runtime: Python drives pi; TypeScript drives pi and opencode; Rust drives goose. Go is a good orchestrator language for exactly this: one static binary, real concurrency, and clean subprocess control. Note that Go is not currently installed on this machine. Step zero is installing it.

Design consequences of a 1 M context at $0.09/M
  1. Context compression is not worth engineering yet. A full 1 M-token context costs 9 cents. Spend the effort on gates instead.
  2. The budget cap is a safety rail, not a cost control. It exists to stop a loop, not to save money. Set it near $2 per run and alert on approach.
  3. The expensive resources are wall time and merge risk, not tokens. Optimize for phases that catch defects.
  4. Attribute anyway. Without per-run cost you cannot answer "was this change worth its tokens," which is the entire point of a factory you run unattended.

11Decisions you must still make

These are the choices that change the architecture. Each is a real fork with a price, not a detail.

1 · Prove a phase before you keep it

The factory will add stages because stages are easy to define and no public system has published an A/B proving a staged pipeline beats one good agent. The burden of proof is on the stages.

Decision: the control arm is a first-class field in the workflow file, and the comparison is a ledger query. Otherwise you carry unmeasured phases for a year.

2 · Who owns the merge line

Either the factory auto-merges when gates pass, or it always leaves a PR for a human. This sets the terminal state machine and the blast radius of a bad run.

Decision: define it now. Auto-merge means "no human required" is real; PR-only halves the value.

3 · Where the agent gets external-system authority

A sandboxed agent has no working GitHub auth path, so the usual pattern is: the agent commits, the host pushes. There is no clean way to give a sandboxed agent write credentials.

Decision: the agent reads external systems through MCP with a scoped short-lived lease, or it gets nothing and the factory performs all I/O. The second is safer and simpler; the first enables triage agents.

4 · Secret custody at the egress

The agent must reach a model provider, and the provider key must not reach the agent. Two shapes exist: a broker the factory calls, which injects the key server-side and records usage; or a key placed in the sandbox.

Decision: the broker. It gives exact per-call cost attribution for free and lets you revoke mid-run. It costs about 300 lines.

5 · Reproducibility of a composition

"Reproduce this run" requires the agent definition, prompts, model, reasoning effort, tool policy, and harness version to hash to a digest stored on the run.

Decision: hash and freeze at dispatch. Cheap now, impossible to retrofit.

6 · What a failed run leaves behind

A failed run is not "no run." It must leave a terminal state, the evidence it gathered, and a distinct operator action for each cause.

Decision: define the terminal states now. Suggested: merged, awaiting_operator, review_blocked, verification_failed, budget_exceeded, interrupted.

7 · Independence of judges

No self-approval: a reviewer must not be the same model family as the builder, and it must be read-only, enforced in code. Same-family review lanes are correlated noise and prove nothing.

Decision: plan a seeded-defect corpus early. It is the only way to learn whether review pays.

8 · Concurrency and the one-writer rule

SQLite in WAL allows many readers and one writer. The safest pattern is physical serialization with a file lock.

Decision: one writer goroutine owns the ledger; one lock per repository, not one global lock. Two runs on different repositories should proceed at once.

9 · Retention and backup

An event row per tool call grows quickly, and history is the one thing you cannot rebuild.

Decision: keep envelopes and phase rows forever; roll raw events to compressed files after 30 days. Back up the SQLite file on a schedule from day one.

10 · Single-tenant or multi-tenant from day zero

A factory your team runs is single-tenant. A factory other people's desktops join as workers is multi-tenant across trust boundaries.

Decision: design the ledger and the egress proxy single-tenant now. Multi-tenant is Proposal C plus an authorization layer, and only that.

Smaller decisions, still real

  • Prompt versioning. Prompts live in the target repository and are reviewed like code.
  • Loop prevention. A PR opened by the factory must not trigger the factory. Exclude the factory's own identity from its triggers.
  • Multi-repository. The lock is per repository and the worktree root is per repository. Design it in now; it costs nothing.
  • The quality-command trap. A placeholder command that exits 0 produces a green phase that ran nothing. Fail closed when the command is unset.
  • Cancellation. Must kill the subprocess tree, not just the parent, and must mark the phase in the ledger. A silent agent hang with an empty trace is a debugging dead end.
  • Deadlines. Every phase needs a wall-clock deadline, and the timeout must be a distinct exit code so the trace shows it.

12Open questions

  1. Is durability a hard requirement or a best-effort property? If hard, R1's test is "stop the host, the run resumes at the correct phase with no duplicate effect," and that single sentence drives the whole design. If best-effort, you may cut the resumed-run machinery and lose little today.
  2. Auto-merge on green, or always hand you a PR? This sets the terminal state machine.
  3. Egress broker, or a key inside the sandbox? The broker costs about 300 lines and buys exact per-call cost attribution plus revocation.
  4. Do agents need external-system tools at all in v1? If no, drop MCP from the critical path and pi becomes as viable as opencode.
  5. Server-rendered UI, or an embedded SPA? Go templates plus one polling endpoint is roughly 400 lines. A React build is a second toolchain. The ledger is one cursor query, so start server-rendered.
  6. Is "run on someone's desktop" a real requirement, or a nice property? If real, it argues for Proposal C's worker flag earlier. If nice, one static binary already gives it for development.
